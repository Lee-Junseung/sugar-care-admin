# Sugar Care Admin — 혈당 관리 서비스 관리자 대시보드

> 가천대학교 팀 프로젝트로 진행한 혈당(당뇨) 관리 서비스 '쏙식'의 관리자용 웹 대시보드.
> 사용자의 혈당·식단·알레르기·목표 데이터를 관리자가 한눈에 모니터링하고, 신고 내역을 관리할 수 있는 화면을 구현.
> React 기반 프론트엔드 개발 담당.

**이 프로젝트를 포트폴리오에 포함한 이유**: 단순히 완성된 화면을 보여주기보다, 실제 설계 문서 대비 구현 결과가 어떻게 달라졌고 그 과정에서 어떤 판단을 내렸는지를 정리해두고 싶었음. 아래 "기획자 관점에서 본 범위 조정" 섹션에 그 판단 과정을 담음.

이 브랜치(`main`)는 실제 백엔드 서버와 연동되는 원본 코드이며, 팀 프로젝트 종료 후 백엔드 서버가 종료되어 현재는 로컬에서 API 연동 화면을 확인할 수 없음.
`demo` 브랜치는 동일한 화면을 mock 데이터로 재현해 백엔드 없이도 바로 실행해볼 수 있도록 만든 버전.

## 프로젝트 소개

Android 및 iOS 모바일 환경에서 당뇨 환자 및 고위험군을 위한 AI 기반 식단·혈당 통합 관리 솔루션 '쏙식'의 관리자 대시보드.

주 사용자는 당뇨병 전단계 인구부터 지속적인 식사 요법과 혈당 관리가 필수적인 1·2형 당뇨 및 임신성 당뇨 환자이며, 모바일을 통해 접속·사용하기 편리하도록 설계됨. 환자의 라이프로그(식단, 혈당)를 체계적으로 관리하기 위해 별도의 관리자 기능을 구성했으며, 사용 편의성과 의학적 정보의 신뢰성, 관리의 지속성을 추구할 수 있도록 개발함.

- 팀 구성: 프론트엔드 2명, 백엔드 2명
- 배포 환경: 별도 백엔드 API 서버 연동 (현재 서버 미운영)

## 주요 화면 / 기능

`App.jsx`의 메뉴 구조 기준으로 구현된 화면.

대시보드
- 서비스 통계 (`ServiceStats`) — 일별 식사 기록 수, 이용자 수 등 종합 통계
  - *왜 필요했나*: 관리자가 서비스 전반의 활성도를 진입 직후 바로 파악할 수 있도록 가장 상단에 배치
- 알레르기 통계 (`AllergyStats`)
  - *왜 필요했나*: 알레르기 유발 빈도가 높은 식품군을 빠르게 파악해, 위험 사용자 대응이나 식단 추천 로직 점검에 활용할 수 있도록 설계
- 혈당 관리 통계 (`BloodSugarStats`) — 당뇨 유형별 시간대별 혈당 추이
  - *왜 필요했나*: 당뇨 유형별로 혈당 이상 추이를 조기에 포착해 관리자가 개입 시점을 판단할 수 있도록 하기 위함
- 인기 음식 통계 (`PopularFoodStats`)
  - *왜 필요했나*: 사용자들이 자주 섭취하는 음식을 파악해, 서비스의 AI 식단 추천 로직을 검증·개선하는 데 참고 자료로 쓰일 수 있도록 함
- 식사 패턴 통계 (`MealPatternStats`)
  - *왜 필요했나*: 식사 시간·빈도 패턴으로 사용자의 규칙적인 식습관 여부를 관리 지표로 삼기 위해 기획됨 (개발 범위 조정으로 미구현 — 아래 "기획자 관점" 참고)

사용자 관리
- 사용자 리스트 (`UserList`) — 검색, 페이지네이션, 상세정보(알레르기/선호음식/목표혈당 등) 조회
  - *왜 필요했나*: 설계서에는 없었지만, 사용자 수가 늘어날 상황을 고려해 페이지네이션을 자체 판단으로 추가함
- 신고 관리 (`ReportManagement`) — 유형별(체중/혈당/식단) 필터링, 정렬, 처리 상태 관리
  - *왜 필요했나*: 신고 유형에 따라 관리자의 처리 우선순위가 달라질 수 있어, 유형별 필터링을 핵심 기능으로 설계

## 기획자 관점에서 본 범위 조정

프론트엔드 개발자로 참여했지만, 포트폴리오 정리 과정에서 "무엇을 만들었는가"뿐 아니라 "왜 이 범위로 결정했는가"를 함께 남기고자 함.

**API 연동 우선순위 조정**
학기 내 완료해야 하는 학사 일정과 팀 규모(프론트엔드 2명, 백엔드 2명)를 고려할 때, 설계서에 정의된 모든 세부 통계 항목을 전부 API로 연동하는 것은 일정상 리스크가 컸음. 이에 따라 관리자가 실제 의사결정에 활용할 핵심 지표(총사용자수, 알레르기 현황, 혈당 평균/고저, 인기 음식 TOP 리스트, 사용자·신고 관리)를 우선 연동 대상으로 선정하고, 그 외 세부 통계(하루 평균 식사 기록수, 요일별 분포, AI 추천 채택률 등)는 화면 완성도를 보여주기 위한 하드코딩 데이터로 대체하는 방향으로 범위를 조정함. 이 과정에서 지도교수의 피드백도 반영해, 남은 개발 기간 안에서 완성도와 범위의 균형을 맞추는 것을 우선했음.

**목표(Goal) 통계 미구현 — 기능 중복 판단**
`GoalStats.jsx`는 사용자 건강 목표를 전체 집계 통계(목표별 분포, 달성률, 월별 추이)로 보여주기 위해 개발했던 화면이나, 개별 사용자의 건강 목표는 이미 '사용자 리스트' 화면에서 확인 가능했음(`user.goal`, 목표 혈당 등). 관리자 입장에서 동일한 정보를 두 화면에서 중복 제공하는 것은 정보 구조상 비효율적이라고 판단해, 별도의 전체 통계 화면으로 확장하지 않고 메뉴 연결을 보류함. 코드 자체는 향후 필요 시 재활용할 수 있도록 남겨둠.

**설계서에 없던 기능을 추가한 경우 — 사용자 리스트 페이지네이션**
반대로 설계서에는 명시되지 않았지만 자체 판단으로 추가한 기능도 있음. 사용자 리스트는 서비스 성장에 따라 조회 대상이 계속 늘어날 화면이라고 판단해, 검색만으로는 한계가 있을 것으로 보고 페이지네이션을 추가로 구현함. "설계서에 명시된 것만 만든다"가 아니라, 화면의 용도를 기준으로 필요한 기능을 판단해 넣은 사례.

**식사 패턴 서비스 전체 미구현 — 범위에서 제외한 이유**
식사 패턴 통계(`MealPatternStats`)는 세부 항목이 6개로 가장 많고, 서비스 통계·혈당관리 통계와 다루는 데이터(식사 기록, 시간대)가 상당 부분 겹치는 화면이었음. 남은 개발 기간 안에 전체를 API로 연동하기보다, 이미 다른 화면에서 유사한 정보를 제공하고 있는 이 화면을 우선순위에서 가장 뒤로 미루는 것이 관리자에게 미치는 실질적 손실이 적다고 판단함.

지금 돌아보면, 이런 범위·우선순위 판단 과정을 개발 당시에 별도 문서로 남기지 않은 점은 아쉬움. 다음 프로젝트에서는 "왜 이 기능을 이번 범위에서 제외했는지"를 요구사항 정의서나 회의록 수준에서 명시적으로 기록하고 싶음.

## 회고: 재검토 중 발견한 문제점

포트폴리오 정리를 위해 코드를 다시 살펴보며 아래 문제들을 발견함. 당시엔 인지하지 못했던 부분으로, 실무였다면 QA 단계에서 걸러졌어야 할 이슈들.

<details>
<summary>발견한 문제 3가지 펼쳐보기</summary>

**1. UI 상태 관리 버그**
로그인 성공 시 `setCurrentSection('ServiceStats')`로 상태를 세팅하는데, 실제 메뉴 id는 `'stats-service'`(kebab-case). 화면 자체는 `switch`문의 `default` 처리로 정상 노출되지만, 로그인 직후 사이드바의 활성 메뉴 하이라이트가 표시되지 않는 버그가 있음. 상태값 네이밍을 메뉴 id와 일치시켰어야 함.

**2. API 실패 시 사용자 피드백 부재**
`axios` 요청 실패 시 `console.error`만 기록하고 화면에는 아무 안내가 없음. 그 결과 실제로는 "데이터 로딩 실패"인데 "총 사용자 수 0명"처럼 진짜 0건인 것처럼 표시됨. 관리자 대시보드에서는 데이터 신뢰성과 직결되는 문제.

**3. 스크린샷에 실제 서버 IP 노출**
위 "스크린샷" 섹션의 이미지들은 실제 서비스 운영 당시 캡처한 것으로, 주소창에 당시 백엔드 서버의 실제 IP가 그대로 노출되어 있음. 해당 서버는 팀 프로젝트 종료 후 종료되어 현재는 접근이 불가능하므로 실질적 위험은 낮지만, 공개 저장소에 인프라 주소를 노출한 것은 좋은 습관이 아니었음. main 브랜치는 원본 보존 목적상 스크린샷을 재촬영하지 않고 이 사실만 명시함.

**개선 반영**
위 문제 중 UI 버그 수정 및 에러 상태 표시 개선은 [`demo` 브랜치](https://github.com/Lee-Junseung/sugar-care-admin/tree/demo)에 반영함. `main` 브랜치는 실제 팀 프로젝트 당시 코드를 그대로 보존하기 위해 별도로 수정하지 않음.
